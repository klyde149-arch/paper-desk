# CLAUDE.md — правила работы в этом репозитории

Этот репозиторий имеет **живой боевой контур**: VPS каждые ~15 минут коммитит и
пушит в `origin/main` состояние торговли реальными деньгами (Bybit + T‑Invest).
Это не абстрактный риск — `origin/main` в норме обгоняет только что клонированный
или давно не обновлявшийся локальный `main` на сотни-тысячи коммитов, потому что
это в основном поток бот-тиков, а не человеческая история.

## Инвариант: боты владеют state, человек/Claude владеет кодом

Три писателя в `origin/main` безопасны друг для друга, потому что каждый коммитит
**свой непересекающийся набор путей**:

| Писатель | Владеет |
|---|---|
| `live-desk-bot` (VPS, Bybit) | `data/live_real/**`, `journal_live.md` |
| `live-desk-bot` (VPS, T‑Invest/RF) | `data/live_rf/**` (кроме `config.json`, `candles/`), `journal_live_rf.md`, `data/rf/manual_close_req.json` |
| `paper-desk-bot` (GitHub Actions) | бумажные `data/**` (всё остальное) |

Это работает, пока **никто не пересекает границу**. Единственный способ сломать
живой контур с локальной/Claude-стороны — самому нарушить этот инвариант:
закоммитить bot-owned state из устаревшего дерева (откатив боевые данные),
`git add data/…` без разбора, или force-push. Ребейз `git pull --rebase --autostash`
на VPS сам по себе не конфликтует между ботами — они не трогают одни и те же файлы.

**Правило:** человек и Claude коммитят только код и конфиг. Никогда — файлы из
таблицы выше (кроме `data/live_*/config.json` — это ручной ramp-конфиг, его
можно и нужно редактировать).

## Протокол работы (обязателен для каждой сессии)

```bash
git fetch origin
git switch -c <branch-name> origin/main   # НЕ от локального main — он может быть устаревшим
# ...правки кода...
git push -u origin <branch-name>
# интеграция в main — через Pull Request, не прямым push
```

- Локальный `main` не используется как рабочая ветка и не обновляется вручную —
  он существует только как исторический указатель; актуальное состояние всегда
  в `origin/main`.
- Каждая параллельная Claude-сессия работает в своей отдельной ветке. Если работают
  несколько сессий одновременно — они не коммитят в одну и ту же ветку.
- Прямой push в `main` не делаем — только через PR (fast-forward/squash). Это даёт
  единую точку интеграции вместо гонки нескольких писателей за один ref.
- После мержа VPS штатно подтянет обновлённый `main` при следующем тике — пути не
  пересекаются с его собственными коммитами, конфликтов не будет.
- Этот файл — тоже код: правится по тому же протоколу.

## Локальная защита (только эта машина, VPS не затронут)

- `.githooks/pre-commit` и `.githooks/pre-push` — блокируют коммит bot-owned state,
  коммит на `main`/из устаревшего дерева, force-push и прямой push в `main`.
  Активируются через `tools/install-hooks.ps1` (ставит `core.hooksPath` — это
  локальная git-конфигурация, в `origin/main` не уезжает и на VPS не действует).
- PreToolUse-хук Claude Code (`tools/claude_git_guard.sh`) — тот же список запретов,
  но денаит git-команду до её выполнения внутри Claude-сессии.
- Оба рубежа no-op для identity ботов (`live-desk-bot`, `paper-desk-bot`) — безопасны,
  даже если случайно окажутся активны на VPS.

Подробности реализации — см. сами файлы в `.githooks/` и `tools/`.
