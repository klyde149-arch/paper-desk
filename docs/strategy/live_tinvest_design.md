## Ключевые дизайн-решения (нейтрализуют главные точки провала)
1. **Polling-first, без стримов.** Каждый минутный тик = полная сверка (портфель + заявки +
   стоп-заявки + маржа, 4–6 unary — в ~10 раз внутри rate-лимитов). «Обрыв стрима без
   восстановления состояния» исчезает как класс: обрыв сети = прерванный oneshot-тик, следующий
   тик всё чинит. Стримы — опциональный ускоритель v2, источником истины не становятся.
2. **Брокерские стоп-заявки (StopOrdersService)**: переживают падение бота/VPS/сети и ночной гэп
   00:30→10:00; хранятся у брокера, не на бирже → перевыставления не жгут лимит транзакций Мосбиржи.
3. **Market-входы в окно 10:01–10:15**: paper исполняет вход по open±SLIP 3bps — спред ликвидных
   фронтов сопоставим. Нет зависших лимиток → флуд-сборы исключены (ratio ~1:1.5 при лимите 10:1).
4. **Латентность не критична by design**: C3b дневная, вход на открытии. Метрики
   t_signal→t_post→t_fill логируются per-заявка (latency_log.csv + trades.json).
5. **Сигналы байт-в-байт = paper**: общий код `tools/lib_rf_signals.ps1` (вынос защищён
   golden-replay), те же данные MOEX ISS, те же непрерывные серии (свой каталог
   `data/live_rf/series`, при старте сидируется копией paper-серий).

## Тик-пайплайн (каждую минуту)
lock → kill-файлы (`HALT`, `HALT_RF_LIVE`, `HALT_RF_CLOSE`=закрыть всё, `HALT_RF_ENTRIES`) →
weekend-гейт (внебиржевые выходные НЕ торгуем) → preflight (GetMarginAttributes; сбой = тик прерван,
вотермарки на месте, алерт на 5-м подряд) → **сверка**: снимок стоп-заявок → TP1-sync (до D5!) →
reconcile → state-machine polling → MTM → governors → расписание MSK:
- **00:20** дневной хук (бар D финален в 00:15): докатка серий + SHA-мысль о кросс-сверке с paper,
  фронты (ISS) + сверка экспираций с API, сигналы Donchian/setA → entry-интенты (исполнение завтра
  06:01, ЕТС-факт — см. ниже), детект роллов (≤4 дн до LASTTRADEDATE), **трейл-люстра — ТОЛЬКО здесь**
  (MFE копится по часовикам, стоп двигается раз в день — ровно как paper), EMA20-выходы →
  exit-интенты, mom-сигнал 1-го торгового дня;
- **09:45** обновление кэша инструментов/ГО + отложенные stop_replace (для стопов, отложенных вне
  сессии/клиринга дневным хуком в 00:20); **06:01–10:15** exits → entries (сайзинг + предиктивный
  ГО-чек; после fill — стоп-заявка В ТОМ ЖЕ тике); **06:05–18:00** роллы; **06:10** mom sells →
  (после подтверждения) buys; **ежечасно** MFE-трекинг + BE-эмуляция TP1 для lots==1 (+эмуляция
  стопов в sandbox); **каждые 15 мин** MTM-снапшот; **23:55** дневной отчёт (латентность, ratio
  заявки:сделки, пик ГО, дрифты, qty0-пропуски) + Telegram.
- Окна и клиринг — боевой факт с 2026-07-17 (ЕТС-2026 торгуется с 06:00-07:00 MSK, значения выше
  сдвинуты со старого дизайна 10:01/19:30 под это): вход/выход-на-открытии 06:01–10:15, роллы
  06:05–18:00, mom 06:10, отчёт 23:55. Клиринг единственный, ночной: 23:48–00:32 — никаких
  постановок.

## State machine заявки
`INTENT →(persist ДО post)→ POSTED → FILLED | PARTIAL(стоп на filled_lots сразу; добор ≤3 попыток) |
REJECTED(без ретрая; roll_open REJECTED = карточка закрывается reason=roll-fail) |
LOST(adopt по операциям / repost ТЕМ ЖЕ order_id ≤3) | EXPIRED(entry живёт только свой день)`.
Терминальные интенты убираются в том же тике. Предохранитель: >20 постановок/день → entries_halt.
postOrder ≠ факт исполнения: подтверждение только через GetOrderState + GetOperations.

## Reconcile (каждый тик; в dryrun — log-only)
Гейт битого снимка: если `GetPortfolio.positions` пуст целиком — сверка тика полностью пропущена
(отложена на следующий), т.к. на реальном счету всегда есть хотя бы валютная (рублёвая) строка;
пустой ответ = транзиентный глюк брокера, а не «все карточки закрылись» (см. инцидент 2026-07-27
ниже). Фьючерсы (строго, эксклюзив бота): **D2** чужая позиция → аварийное закрытие + halt; **D4**
карточка без позиции у брокера → операция закрытия из operations подтверждена, но причина
`'stop'` пишется только если цена сделки не лучше текущего стопа карточки И сама стоп-заявка у
брокера уже не живёт — иначе (закрыли руками в приложении/сработало что-то ещё, а стоп-заявка
осталась висеть или цена выхода строго лучше триггера) причина `'manual-ext'`, осиротевшая
стоп-заявка снимается, идёт отдельный алерт (см. инцидент 2026-08-11 ниже) — оба случая штатные,
без халта; **либо**, если ни позиции, ни операции нет **два тика подряд** (`d4_fails` по образцу
D6), — карантин (сторож стопа D6 выключается для этой карточки) + halt входов; **D5** лоты ≠ (не
объяснимо intents/TP1) → усечь к брокеру; **D6** позиция без стоп-заявки → перевзвод немедленно,
2-я подряд неудача → аварийное закрытие. Карантин и халт-по-дрифту (`entries_halt.reason` вида
`D2 …`/`D4 …`) снимаются автоматически, как только на очередном тике расхождение больше не
подтверждается — ручная правка `data/live_rf/portfolio.json` для этого не нужна. Halt входов
блокирует только новые входы: постинг pending exit-интентов (например `trail-ema20`) идёт до
проверки halt, открытые позиции продолжают вестись. Акции: real ≥ bot — норма; real < bot → усечь
бот-леджер + алерт; продажи только ≤ bot_lots.

## Сайзинг и governors
- `rub_per_pt = min_price_increment_amount / min_price_increment`;
  `lots = floor(riskRub / (stopDist_pts × rub_per_pt))`, зеркало кэпа MAXLEV=3 по нотионалу,
  lots==0 → SKIP qty0 (лог+счётчик). setA stopDist — от фактического филла (max(свинг, 1×ATR)).
  **Размер сделки задаёт `eq_rub` рукава** (`riskRub = eq_rub × risk_pct`) — не `base_rub` в
  конфиге и не потолок ГО ниже; это разошлось на практике и стоило ребейза 2026-08-12 (см. врезку).
- Sleeve-леджеры: изначально core 700k, setA 700k (= `base_rub`). **2026-08-12 core и setA
  ребейзнуты на полный капитал бота 1 106 481 ₽** (решение пользователя, коммит `4d984ca8e`) —
  виртуальные леджеры росли только на своём P&L, а капитал счёта ещё и на пополнениях, поэтому
  рукава отстали и риск размылся до 3.4%/1.3% фактического капитала вместо заложенных 5%/2%.
  Механика: цель приходит через `data/live_rf/config.json` → `sleeve_rebase {id, core, setA}`,
  `Invoke-SleeveRebase` применяет её РОВНО один раз по вотермарке `watermarks.sleeve_rebase_id`
  (правка `portfolio.json` через git не работает — VPS считает свой state авторитетным и
  перезапишет ближайшим тиком). `month_start_eq`/`day_start_eq` едут тем же множителем, что и
  `eq_rub`, иначе доходность рукава показала бы фантомный скачок. **mom = `base_rub`×0.5 = 350k
  и инвестируется целиком** (эквивалент paper: полный рукав с весом 0.5 в профиле; половинить и
  снова взвешивать — двойное занижение) — mom НЕ ребейзился, база осталась 700k. Профиль —
  помесячно-аддитивно как paper.
- ГО: вход ⇔ go_after ≤ 60% × (`bot_capital_rub` − стоимость bot-акций − резерв 50k); мониторинг
  каждый тик; >60% → entries_halt; >75% → LIFO-закрытие. **С 2026-08-12 бюджет считается от
  реального капитала бота `bot_capital_rub`** (`Set-BotCapital`, растёт вместе со счётом), а не от
  фиксированного `base_rub` — старый потолок не был ограничителем сам по себе (занятое ГО 124k из
  лимита 390k), но не рос со счётом. Фолбэк на `base_rub` — только на первом тике после деплоя, пока
  `bot_capital_rub` ещё не посчитан. Paper-идентично: day-halt рукава −6% (снимает только входы),
  MAXCONC=3, 1 позиция/символ, re-arm. Дополнительно: профиль-день −8% → entries_halt; **hard −35%
  от пика** (`capital_peak_rub`, реальный капитал брокера) → закрыть всё + HALT_RF_LIVE.

## Роллы
Триггер как paper (≤4 дн до LASTTRADEDATE или биржа сменила фронт; рескейл серии тем же кодом —
иначе разойдутся сигналы). Исполнение в окно 06:05–18:00: cancel стопа → roll_close market → FILLED →
roll_open market (лоты = сохранение нотионала, мин 1) → новый стоп. Новый сигнал в зоне ролла →
вход сразу в следующий контракт (задокументированная исполнительская дивергенция). Никогда не
открывать контракт с ≤4 дн до LT.

## Режимы (env TINVEST_MODE)
- **dryrun** — мутирующие вызовы перехватываются ДО любого транспорта (WOULD CALL в
  dryrun_calls.log), исполнение симулируется по референс-цене, reconcile log-only;
- **sandbox** — песочница; StopOrders там нет → `config.json: {"emulate_stops": true}` (бот-сайд по
  часовикам, код общий с BE-логикой lots==1); заявки песочницы исполняются мгновенно по последней цене;
- **prod** — реальные заявки. Оверрайды фаз — `data/live_rf/config.json` (whitelist,
  max_lots_override, mom_enabled и т.д.), без правки кода.

## Осознанные компромиссы (меряются недельной декомпозицией дивергенции live vs paper futC3b)
- Целые лоты: эффективный риск ≤ paper (floor); TP1 при lots==1 → только BE-перенос.
- Вход в следующий контракт в зоне ролла (paper: вход во фронт + платный ролл назавтра).
- Брокерский stop-market real-time vs paper «касание часовика» — направленно нейтрально.
- Комиссии: до Phase 1 модель 1bps (fee_est) — заменить фактом из operations/тарифа.
- Hard-halt −35% внутри бэктест-DD 40–44% — выбор пользователя.

## Инцидент 2026-07-27 — ложный D4-карантин на L00011 (GDU6)
Один тик (13:08 UTC) получил от `GetPortfolio` ответ с пустым `positions` (тот же класс глюка,
что 2026-07-23 у `Set-BotCapital` — там уже была защита, у reconcile не было). Карточка L00011
(золото, шорт 1 лот) реально была жива у брокера весь период — на следующем же тике сверка сама
сошлась (`drift.D4` остался 1, не рос), но карантин и `entries_halt` не снимались автоматически:

## Инцидент 2026-08-04 — цена входа: «подано» вместо «исполнено»
Записанные цены входа систематически ложились **вне диапазона рынка и всегда в худшую для
бота сторону**: Si @81794 при максимуме контракта за 30 дней 81650, CNY @12.111 при 12.089,
а июльский шорт GOLD @4037.9 при минимуме дня 4041.3. Ни одного бара, где рынок доходил бы
до записанной цены.

Причина в `Get-FillPxPerUnit`: лестница кандидатов брала первым `initial_order_price_pt` —
это цена **поданной** заявки, а у рыночной заявки MOEX она идёт с защитной полосой (~0.2% в
сторону сделки). Реально исполненная цена лежит в `executed_order_price` и стояла в лестнице
третьей, поэтому не выигрывала никогда. Расхождение в 0.2% беспрепятственно проходило
30%-ые ворота, поставленные после инцидента L00008.

Почему не всплыло само: `Invoke-Reconcile` сверяет **лоты, а не цены**. Ошибка не рождает ни
одного дрифта и тихо живёт в трёх местах — P&L (фантомный минус сразу после входа, 04.08 это
~7.3k ₽ на двух позициях), стоп (считается от входа, поэтому стоял на ~10% теснее правила
2xATR) и статистика контура (`realized_rub` занижен на каждой закрытой сделке).

Фикс двойной:
1. Порядок кандидатов в лестнице: исполненная цена первой, поданная — фолбэком. Расхождение
   между ними пишется в `tick_log.txt` всегда, чтобы смена семантики у брокера была видна
   сразу, а не через месяц.
2. `Confirm-EntryPx` — подтверждение цены входа по **операциям брокера**, тому же источнику,
   которому движок уже верит при стопах, TP1 и adopt. Один раз на карточку, с явным запросом
   окна от времени сделки (кэш `Get-OpsSince` скользит на час и вход из него выпадает).
   Чинит цену, комиссию, MFE и TP1; **живую стоп-заявку намеренно НЕ двигает** — сдвиг защиты
   на реальных деньгах остаётся решением пользователя, а дневной трейл-хук всё равно приведёт
   стоп к правилу. Расхождение стопа проговаривается в журнале и алерте.

Это второй случай, когда семантика полей T-Invest оказалась не той, что ожидали (первый —
L00008, `initial_order_price_pt` за лот, а не суммой). Вывод тот же: **ответ на заявку не
является источником истины об исполнении, источник истины — операции**. Регрессия:
сценарии `entry-px-exec` и `entry-px-repair` в `tools/test_live_rf_scenarios.ps1`.

## Инцидент 2026-08-11 — ручное/внешнее закрытие позиции засчитывалось как срабатывание стопа
Ветка **D4** (позиции у брокера нет, операция закрытия есть) писала причину `'stop'` безусловно,
не глядя ни на цену сделки, ни на то, жива ли ещё у брокера стоп-заявка карточки. Стоп-маркет
физически не может исполниться лучше своего триггера (лонг срабатывает при падении цены до
уровня и заливается по биду, то есть на уровне или хуже, шорт зеркально) — поэтому цена выхода
строго лучше стопа однозначно означает, что закрыл не стоп. Проверка по всем шести живым
сделкам, закрытым с 2026-07-21 по 2026-08-07 (L00008, L00011, L00017, L00018, L00021, L00022,
стопы взяты из записей «ВХОД» в `journal_live_rf.md`), показала: **ни одна не была закрыта
стопом** — все выходы строго лучше уровня стопа карточки на момент закрытия. Вечерние отчёты и
дашборд четырежды сообщили «сработала стоп-заявка» по прибыльным сделкам, форвард-тест
оказался неотличим от бэктеста стратегии в этих шести случаях. Побочный дефект той же ветки:
при внешнем закрытии стоп-заявка бота оставалась висеть у брокера — при достижении уровня она
открыла бы обратную позицию (→ D2 «чужая позиция» → аварийное закрытие + halt).

Фикс: `Test-StopCouldFire` в `tools/live_rf_engine.ps1` сравнивает цену закрытия с текущим
`stop_px_pts` карточки (уровень уже учитывает трейл-люстру ядра и перенос в БУ по TP1 сетапа А,
допуск 0.1% на округление к шагу цены). D4 клеймит `'stop'`, только если цена не лучше уровня
**и** стоп-заявка карточки уже не значится живой в `GetStopOrders`; иначе причина `'manual-ext'`,
осиротевшая стоп-заявка снимается (`CancelStopOrder`), отдельный алерт объясняет пользователю,
что произошло. `RfReasonRu` получил точный кейс `'manual-ext'` → «закрыто вне бота (стоп-заявка
не срабатывала)», записи сделок — поле `stopPx` (уровень стопа на момент закрытия, не сохранялся
раньше — именно поэтому этот аудит пришлось делать по журналу, а не по данным). Симметрично
поправлен Bybit-контур (`tools/live_engine.ps1`, филл без нашего `linkId`) — по тому же принципу,
но там аудит истории правок не потребовал: все прошлые `stop`-записи там — убытки ≈−1R, настоящие
срабатывания.

История: `data/live_rf/trades.json` — все шесть записей перелейблены `stop` → `manual-ext`, P&L и
капитал не тронуты (деньги реальные, уже учтены). Старые строки `journal_live_rf.md` и вечерних
отчётов намеренно не переписаны — лог фиксирует, что бот говорил тогда; факт задокументирован
здесь и отдельной записью в конце журнала. Регрессия: сценарии `d4-manual-ext`, `d4-stop-alive` в
`tools/test_live_rf_scenarios.ps1` (плюс `d4-confirmed` как якорь — настоящий стоп не должен
перестать классифицироваться как `'stop'`).
