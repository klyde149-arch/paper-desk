# RF-LIVE runbook — запуск C3b на реальном счёте Т-Инвестиций

Контур: `tools/live_rf_engine.ps1` (дизайн: `docs/strategy/live_tinvest_design.md`).
Фазы идут строго по порядку; gate-критерии каждой фазы — в дизайн-доке. **Текущий статус: в проде
с 2026-07-17** (`TINVEST_MODE=prod`, счёт 2154036525) — фазы 0-4 ниже пройдены, это исторический
порядок запуска. Актуальная фаза — 5 (эксплуатация, дизайн-док).

## Phase 1 — readonly-токен (ПРОЙДЕНО)
1. В личном кабинете Т-Инвестиций создать **READONLY**-токен (не полный!).
2. Локально: `$env:TINVEST_TOKEN='...'; powershell -File tools\tinvest_selftest.ps1`
   → список счетов (взять `TINVEST_ACCOUNT_ID`), аудит канонического универсума (12 фьючерсов + 11
   акций, `$ASSETS`/`$TICKERS` в `tools\lib_rf_signals.ps1` — было 8+12 до расширения 2026-08-12),
   клиринги, латентность.
3. На VPS: добавить в `/etc/trading-live.env` строки `TINVEST_TOKEN=`, `TINVEST_ACCOUNT_ID=`,
   `TINVEST_MODE=dryrun` (файл уже root:root 600). Прогнать selftest с VPS — **главный probe**:
   если хост недоступен с зарубежного IP → план Б (RU VPS ~200–500 ₽/мес или локальный Windows + Task Scheduler).
4. Установить юниты (НЕ раньше):
   ```
   sudo cp deploy/live-rf-tick.service deploy/live-rf-tick.timer /etc/systemd/system/
   sudo cp deploy/rf-bake.service deploy/rf-bake.timer deploy/tick-alert@.service /etc/systemd/system/
   sudo systemctl daemon-reload && sudo systemctl enable --now live-rf-tick.timer rf-bake.timer
   # ОБЯЗАТЕЛЬНО после любой правки юнита - systemd игнорирует непонятые ключи МОЛЧА:
   sudo systemd-analyze verify /etc/systemd/system/live-rf-tick.service \
        /etc/systemd/system/rf-bake.service /etc/systemd/system/tick-alert@.service
   ```
   Пустой вывод `systemd-analyze verify` = юниты валидны. Проверка не формальность: при выкатке
   2026-08-18 `OnFailure=` был по ошибке положен в секцию `[Service]` вместо `[Unit]`, и systemd
   молча его отбросил — алерт о падении тика не работал бы, а выглядело бы всё установленным.
   `chmod +x` тут НЕ нужен и вреден: бит исполнения лежит в самом коммите (100755). Ручной chmod
   создаёт вечную незакоммиченную mode-диффу, которую `git pull --rebase --autostash` в тике рано
   или поздно роняет — так контур молча умер на 27 ч, инцидент 2026-08-11.
5. DRYRUN ≥10 торговых дней: движок тикает, сигналы пишутся, заявки — только WOULD CALL
   (`data/live_rf/dryrun_calls.log`). Ежедневно сверять сигналы с paper (`journal.md` vs `journal_live_rf.md`).
6. Закрыть реестр открытых вопросов дизайн-дока, обновить `$CLEARING` в движке по TradingSchedules
   (большинство закрыто — актуальный статус: «Реестр вопросов» в дизайн-доке).

## Phase 2 — sandbox (ПРОЙДЕНО)
1. Токен песочницы → `TINVEST_SANDBOX_TOKEN=`, `TINVEST_MODE=sandbox`; пополнить песочный счёт.
2. `data/live_rf/config.json`: `{ "emulate_stops": true }` (StopOrders в песочнице нет).
3. ≥15 торговых дней: входы/стопы/ролл/mom-ребаланс; kill-drill всех 4 файлов:
   `data/HALT`, `data/HALT_RF_LIVE`, `data/HALT_RF_CLOSE`, `data/HALT_RF_ENTRIES` (создать в main → git pull доставит).

## Phase 3 — боевой микро (~20–50k ₽ задействовано, ПРОЙДЕНО)
1. **Полный** (trade) токен; РЕКОМЕНДАЦИЯ: без вывода средств, если брокер позволяет ограничить.
2. `TINVEST_MODE=prod`; `data/live_rf/config.json`:
   `{ "whitelist": ["CNY","NG"], "max_lots_override": 1, "mom_enabled": false }`
3. Прожить вживую: вход → стоп (в т.ч. ночной гэп) → трейл → BE → ролл → kill-drill → «выдернуть сеть» mid-tick.
4. Сверить комиссии факт (operations) с моделью `fee_est` в движке — поправить.

## Phase 4 — рабочий капитал (ПРОЙДЕНО)
`config.json`: `{ "base_rub": 175000 }` → 2 недели → `350000` + `"mom_enabled": true` → 2 недели → `700000`, убрать whitelist/override.
Гейт ступени: дивергенция live vs paper ≤2% сверх объяснимой; пик ГО ≤60%; 0 неразрешённых дрифтов.

**2026-08-12 (сверх исходного рампа):** `base_rub` остаётся 700000 (это база mom-рукава и фолбэк
бюджета ГО до первого расчёта `bot_capital_rub`), но core и setA больше не читают `base_rub`
напрямую — размер сделки задаёт `eq_rub` рукава, и оба ребейзнуты на полный капитал бота
(1 106 481 ₽ на дату решения). Потолок ГО тоже переведён на `bot_capital_rub` вместо
фиксированного `base_rub` — растёт вместе со счётом. Подробности — «Сайзинг и governors» в
дизайн-доке.

**Как менять масштаб рукавов теперь:** ТОЛЬКО через `config.json` → `sleeve_rebase: {"id": "...",
"core": N, "setA": N}` с новым `id` при каждой правке. Прямая правка `data/live_rf/portfolio.json`
через git не работает — VPS считает свой state авторитетным и перезапишет его ближайшим тиком;
движок применит цель ровно один раз по вотермарке `watermarks.sleeve_rebase_id`.

## Риск-политика `rf-early-exit-v1`: режимы, включение, откат

Механика — в дизайн-доке, раздел «Риск-политика». Здесь только эксплуатация.

**Режимы:** `off` (блока нет — поведение прежнее) → `shadow` (заявки по прежним правилам, кандидат
политики считается рядом и пишется в журнал) → `cap` (работает ТОЛЬКО предел стопа; объём, бюджеты
риска и дневной предохранитель остаются прежними) → `pilot`/`active` (новые входы по политике
целиком). Пилот включается ТОЛЬКО отдельным решением пользователя на конкретный конфиг.

**Важно про `cap`:** поля `risk_pct` и потолки в конфиге по схеме обязательны, но в этом режиме
НЕ применяются. Проверить, что именно действует, можно двумя способами: алерт смены режима пишет
«ТОЛЬКО предел стопа…», а в `portfolio.json` → `risk_budget.budgets_enforced` стоит `false`.
Карточки этого режима получают `risk_policy.mode = 'cap'` и не имеют `risk_budget_rub`.

**Включение — через `data/live_rf/config.json` в git** (VPS конфиг не пишет, только читает):
1. Добавить или изменить ТОЛЬКО блок `rf_risk_policy`. Остальные ключи (`funding`, `margin_disabled`,
   `sleeve_rebase`, `auto_rebase`, `go_cap_pct`) не трогать.
2. Закоммитить и запушить: код и конфиг приедут ближайшим тиком (`git pull` в начале тика).
3. Проверить на VPS, только чтение:
   - `grep risk-policy data/live_rf/tick_log.txt | tail -3` — строка «режим …, хеш …»;
   - в `data/live_rf/portfolio.json`: `risk_policy.applied_hash` совпадает с посчитанным локально
     (`Resolve-RfRiskPolicy` из `tools/lib_rf_risk.ps1`), `rejected_reason` пуст, заполнен `risk_budget`;
   - `data/live_rf/risk_log.json` — события `config` и `decision`;
   - в `latency_log.csv` нет новых мутирующих методов: shadow заявок не шлёт.

**Конфиг отклонён.** Движок ставит `entries_halt` с причиной `RP конфиг: …` и НЕ возвращается к
прежнему риску 5%. Причина видна в `portfolio.json` → `entries_halt.reason` и в вечернем отчёте.
Исправленный конфиг снимает халт сам следующим тиком.

**Откат:**
- быстрый — `"mode": "off"` или убрать блок; действует со следующего тика. Карточки, открытые по
  политике, продолжают вестись по закреплённым на них правилам;
- пауза входов без отката — kill-файл `data/HALT_RF_ENTRIES` (сопровождение позиций продолжается);
- откат кода — в shadow безопасен (у карточек нет полей политики); после пилота только после закрытия
  таких карточек либо на версию, которая их понимает.

**Чего политика не делает:** не закрывает открытые позиции, не трогает их стопы, не меняет сигналы и
бумажный контур. Если старые позиции заняли весь бюджет риска, новые входы просто ждут освобождения.
Всё, что описано ниже, касается ТОЛЬКО карточек, открытых самой политикой (`pilot`/`active`), — в
`shadow` ни одно из этих действий не выполняется.

**Плановые выходы политики** (в трейд-логе видны как причины `stop-cap-breach` и `risk-excess`): первая
— рынок ушёл за стоп, пересчитанный от подтверждённой операциями цены входа; вторая — риск позиции
превысил заложенный бюджет, и его не хватило даже на один лот. Оба закрытия ПЛАНОВЫЕ: пауза входов при
них не включается, в отличие от аварийных закрытий по расхождению (D2/D6). Частичное сокращение видно
строкой `REDUCE …` в `tick_log.txt` и отдельным сообщением клиенту; стоп при этом перевыставляется на
остаток позиции.

**Цена входа не подтвердилась.** Статус `entry_px_status: unresolved` в `portfolio.json` означает, что
операции брокера не сошлись с объёмом входа. Риск такой позиции считается неизвестным, поэтому новые
входы ждут до ручной сверки; позиция и её стоп-заявка не трогаются, движок цену больше не запрашивает.
Разбор: сверить цену и объём входа в приложении брокера и решить, закрывать позицию или продолжать —
автоматической починки здесь намеренно нет, это реальные деньги.

## Ограничение счёта: VTBR и SBRF торгуются только в ЛОНГ

**Боевой факт 2026-08-27** (отказы `i00041` 26.08 и `i00042` 27.08 по `VBU6`).

VTBR и SBRF — единственные в каноне **поставочные** фьючерсы (`futuresType =
DELIVERY_TYPE_PHYSICAL_DELIVERY`; остальные десять расчётные). На экспирации шорт по такому
контракту превращается в продажу самих акций — «с вашего счета будет продан базовый актив»
(справка Т-Банка, `help/brokerage/account/forts/trade-futures`). Акций VTBR/SBER на счёте нет,
значит брокеру пришлось бы открыть непокрытый шорт по бумаге. **Маржинальная торговля на счёте
выключена** (`GetMarginAttributes` → `30051 Account margin status is disabled`, зафиксировано как
`margin_disabled: true`), поэтому T-Invest отбивает такую заявку ещё на постановке:
`PostOrder` → HTTP 400, `30051`.

Лонг ограничения не имеет: на экспирации бумаги покупаются за рубли, заём не нужен.

**В коде:** `$LIVE.long_only = @('VTBR','SBRF')` и `Test-SideAllowed` в `tools/live_rf_engine.ps1`.
Шорт-сигнал по этим активам гасится на трёх сигнальных путях (core @close, setA @close, вечерний
same-day) с записью `SKIP long-only ...` в `tick_log.txt`; на постановке заявки стоит дублирующая
проверка на случай интента, восстановленного из старого state. Выходы, стопы и роллы гейт не
трогает — он живёт только на пути входа. Список правится через `config.json` → `long_only`.

Гейт намеренно НЕ в `lib_rf_signals.ps1`: это свойство боевого счёта, а не стратегии. Paper-контур
и бэктест продолжают считать обе стороны, иначе бенчмарк перестанет быть сравнимым с live.

**Следствие для стратегии — посчитано 2026-08-27, эдж НЕ пострадал.** Разбор:
`docs/backtests/long_only_vtbr_sbrf_2026-08.md`. Ограничение улучшает результат на всех
метриках: полный период 4.15 → 5.58 %/мес при просадке 44.0 → 37.9 %, резерв 0.79 → 2.77 %/мес.
Шорты по этим двум исторически теряли деньги (25–27 % побед против 46–60 % у лонгов, −7.7R за
35 сделок) и занимали слоты. Эффект адресный: плацебо-прогоны на других парах дают разброс
вокруг базы, а long-only на всех 12 — только 4.59 %/мес.

**Поэтому включать маржинальную торговлю ради этих шортов не нужно.** Она сняла бы ограничение,
но меняет риск-профиль всего счёта (становятся возможны непреднамеренные плечевые и непокрытые
позиции), а покупать этим отрицательный эдж смысла нет.

## Схема политики 2: выделенная база и выключатели рукавов (этап 2, 2026-09-20)

`schema_version: 2` добавляет два поля. Версия 1 остаётся валидной и означает прежний смысл:
база = проверенный капитал счёта, оба рукава торгуют.

**`allocated_capital_rub`** — явная сумма, которой боту разрешено рисковать. Эффективная база =
`min(выделенная, проверенный капитал счёта)`. Пополнение счёта потолок НЕ поднимает — в этом и
смысл поля; падение доступного капитала базу опускает. Личные активы пользователя в
`bot_capital_account_rub` и так не входят. В `risk_budget` видно, что именно связывает базу:
`capital_binding` = `allocated` или `verified`, рядом `capital_allocated_rub` и
`capital_verified_rub`.

**`core.new_entries` / `setA.new_entries`** — `off | observe | live`. Выключатель касается ТОЛЬКО
новых входов: стопы, сопровождение, выходы и сокращение по бюджету у открытых позиций работают
как обычно. Проверяется дважды — при рождении намерения и в единственной точке отправки
(`Invoke-EntryIntentPost`), потому что отложенный интент мог родиться, когда рукав ещё торговал.
В `schema_version: 2` поле `setA.new_entries` обязательно: молча считать рукав торгующим нельзя.

Оба поля входят в хеш политики — смена базы или выключателя меняет отпечаток, и карточки,
открытые по прежним правилам, это видят.

**Важно про режимы:** сами лимиты (0,5% на сделку, 3% суммарно, 1,5% на валютную группу, дневной
предел 2%) применяются только в режимах `pilot`/`active`. В режиме `cap` политика ставит ТОЛЬКО
предел стопа, а объём и потолки остаются прежними — в `risk_budget` это видно как
`budgets_enforced: false`. `pilot` и `active` в коде ведут себя одинаково; `pilot` — метка для
малого пилота.

Конфиг пилота по плану восстановления:

```json
"rf_risk_policy": {
  "schema_version": 2, "mode": "pilot",
  "allocated_capital_rub": <выделенная сумма>,
  "core": { "stop_cap_pct": 0.02, "risk_pct": 0.005, "new_entries": "live" },
  "setA": { "stop_cap_pct": 0.02, "risk_pct": 0.005, "new_entries": "off" },
  "futures_open_risk_cap_pct": 0.03, "fx_same_direction_cap_pct": 0.015,
  "daily_entry_loss_halt_pct": 0.02
}
```

плюс `"auto_rebase": { "enabled": false }` — автоматическое увеличение базы при пилоте выключено.

Это ограничения сохранения капитала, а не найденные оптимальные параметры доходности: 3% —
верхний предел, а не целевая загрузка.

## Денежный учёт и его проверка (этап 1 плана восстановления, 2026-09-20)

«Результат бота с запуска» собирается из четырёх источников: сведённая на клирингах вариационка
(`broker_ledger.varmargin_rub`), несведённая переоценка открытых позиций
(`capital_breakdown.futures`), фактические комиссии бота (`broker_ledger.fees_rub`) и разовые
ручные коррекции (`manual_adjustments`). BUY/SELL по фьючерсам в итог НЕ идут: их `payment` —
номинал контракта, а не денежный поток. Дивиденды, купоны, налоги и комиссии по бумагам
пользователя к результату бота не относятся и считаются отдельно (`fees_other_rub`).

**Проверка воспроизводимая:** снять выгрузку `tools/rf_broker_dump.ps1` (read-only, только с
`TINVEST_MODE=dryrun`), затем

```
pwsh -NoProfile -File tools/rf_money_reconcile.ps1 -Snapshot <каталог выгрузки>
```

Скрипт кладёт рядом `MONEY_RECONCILIATION_RU.md` и `money_reconciliation.json`: сверяет леджер
движка с операциями брокера построчно, отдельно показывает личные доходы и пополнения/выводы и
сравнивает оценку по карточкам с деньгами брокера. Выход с кодом 2 = расхождение, разбирать до
повышения режима. Сверка 2026-09-20 на снимке за 10.07–20.09: вариационка и комиссии сходятся
с операциями брокера до копейки.

**Почему оценка по карточкам никогда не совпадёт с деньгами брокера точно:** `pnlRub` в
`trades.json` считается по стоимости пункта на момент закрытия, а брокер сводит вариационку
каждый день по своей. Это два разных вопроса, а не проверка одного другим.

### Гашение ошибочной ручной коррекции

`manual_adjustments` заводились вручную, когда вариационка закрытой позиции якобы не доехала до
леджера. Запись `manual-2026-09-09-NG-close` (−80 244,41 ₽) оказалась **двойным учётом**: её
автор смотрел клиринг даты закрытия (09.09, там +4 432,92), а брокер списал газовый убыток
вариационкой днём раньше — 08.09, −76 692,78 ₽. Фьючерс рассчитывается ежедневно, а не в момент
закрытия.

Гасится конфигом — править `portfolio.json` руками нельзя, его перезаписывает своим тик на VPS:

```json
"manual_adj_supersede": {
  "id": "2026-09-20-gas-double-count",
  "targets": [ { "adj_id": "manual-2026-09-09-NG-close", "basis": "..." } ]
}
```

Движок (`Invoke-ManualAdjSupersede`, конфиг + вотермарка = ровно один раз) обнуляет сумму,
сохраняет прежнее значение в `rub_original`, ставит `status='superseded'` и основание в
`superseded_by`. Запись НЕ удаляется: удалить — потерять след ручного вмешательства. Повтор
безопасен. Потребители (`bake_rf_candles.ps1`, Mini App) погашенные записи в итог не берут.

## Аварийные процедуры (в любой момент)
- **Стоп входов**: создать `data/HALT_RF_ENTRIES` (позиции живут, стопы у брокера).
- **Пауза входов держится независимо от других причин** (этап 0 плана восстановления, 2026-09-20).
  `entries_halt` хранит СПИСОК причин `reasons[] = {code, text, since}`; снятие одной причины не
  снимает остальные. Коды: `ops` (kill-файл), `go`, `day`, `D2`/`D4:<карточка>`/`D5R:<карточка>`,
  `rp_config`, `rp_invariant`, `orders_day`, `emergency:<карточка>`, `dd_suspicious`.
  Поля `active`/`reason`/`since` остались для дашборда и отчётов: `reason` — текст самой ранней
  действующей причины, суффикс `(+N)` означает, что причин больше одной. До этой правки вторая
  причина молча терялась, и снятие первой открывало входы при лежащем kill-файле.
- **Полный стоп контура**: `data/HALT_RF_LIVE` (бот не тикает; позиции защищены брокерскими стопами).
- **Закрыть всё немедленно**: `data/HALT_RF_CLOSE` → бот закроет рыночными и остановится.
- Руками: `sudo systemctl stop live-rf-tick.timer`; позиции всегда можно закрыть из приложения Т-Инвестиций
  (после ручных действий НЕ включать бота до сверки: чужие изменения он увидит как дрифт D2/D4/D5).
  Закрытие позиции из приложения ловится как D4 и пишется в `data/live_rf/trades.json` с причиной
  `manual-ext` (не `stop`), а живая стоп-заявка на неё снимается автоматически — см. инцидент
  2026-08-11 в дизайн-доке.
- Телеграм-алерты идут на каждый дрифт/халт/аварийное закрытие (lib_alerts, тот же бот, что крипта).
- **D4-карантин и дрифт-халт (`entries_halt.reason` вида `D2 …`/`D4 …`) снимаются АВТОМАТИЧЕСКИ**,
  как только расхождение перестаёт подтверждаться на очередном тике — правка `portfolio.json`
  руками не нужна (было не так до фикса инцидента 2026-07-27, см. дизайн-док). Разовый D4-алерт не
  требует действий: подождать 1-2 тика (15-30 мин) и проверить, снялся ли `entries_halt.active` в
  `data/live_rf/portfolio.json` / вечернем отчёте. Если карантин НЕ снимается сам за несколько
  тиков — это уже настоящее расхождение, тогда см. «проверьте счёт вручную» из алерта.

### Два потока в Telegram: владелец и клиент

С 2026-08-26 бот шлёт **разный** текст двум получателям (`Invoke-DailyReport`, `Alert`
в `tools/live_rf_engine.ps1`):

| | `TG_CHAT_ID` — владелец | `TG_CHAT_ID_FUT` — клиент |
|---|---|---|
| Вечерний отчёт | полный (`$txt`) | без служебных строк (`$txtClient`) |
| Суточная проверка готовности / худший случай ГО | да | **нет** |
| Расхождения с брокером `D2/D4/D5/D6` | да | **нет** |
| Капитал, P&L, позиции, сделки, ГО занято, статус входов | да | да |
| Алерты по сделкам (вход, выход, TP1, аварийное закрытие, стоп −35 %, ГО-трим) | да | да |
| Технические алерты (роллы, отказы брокера, потерянные стопы, карантин по дрифту, ребейз, связь) | да | **нет** |
| «⚠️ Проверка вечернего отчёта» (LLM-верификатор) | да | **нет** |

Как это устроено:

- **Отчёт.** Служебные строки помечаются по индексу в `$opsIdx` сразу после `$L.Add(...)`;
  клиентский текст = `Get-ClientLines $L $opsIdx` (`tools/lib_engine.ps1`). Добавляете новую
  служебную строку — добавьте следом `[void]$opsIdx.Add($L.Count - 1)`, иначе она уйдёт клиенту.
- **Алерты.** `Alert` принимает `[switch]$Client`. **По умолчанию алерт НЕ клиентский** —
  дефолт выбран так, что забытая пометка даёт клиенту недосказанность, а не утечку технической
  кухни. Новое событие «по деньгам» помечайте `Alert -Client (...)`.

Проверять после правок: `powershell -File tools\test_live_rf.ps1 -Only report`.
